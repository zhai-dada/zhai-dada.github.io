前言#

今天想要学习一下 KDB / KGDB 进行内核调试，于是在内核中开启了 KDB / KGDB 相关的内核选项然后重编内核替换到了板子中，重启之后系统报错触发！

排查过程#

1.分析当前报错信息#

分析当前报错信息什么都没看出来，配合kdb的ps bt等指令，只是确定是 insmod 加载驱动的时候报错的。进程是启动时自动启动的内核加载的脚本。

    CPU: 4 PID: 418 Comm: insmod Tainted: GF       W         5.10.4-9b2d4188ebf6-sophon-custom #5

    resolve_symbol+0x110/0x3b0

因为当前板卡启动时加载了很多官方的驱动，然后我将内核切换到之前的版本然后到系统中将启动时加载的驱动全部关掉，再去启动带有 KDB 功能的内核版本。

重启之后执行 lsmod 之后触发 panic ！排查之后发现是有一个驱动是其他脚本中加载的，将其关闭之后再次重启。重启之后内核没有出现报错，lsmod 也正常。

3.定位问题#

Linux 内核用 struct module 描述每个已加载模块。每个 .ko 文件内部都包含一份该结构体的副本（__this_module）。内核加载模块时，会将驱动中的 modules 结构体连接到当前系统的 modules 链表，lsmod 就是根据链表来访问的，访问信息会按照当前内核编译时的 modules 布局去读取这份副本。

怀疑是 struct module 布局不一致。KDB 需要在内核编译时启用一系列配置，这些配置会改变内核中某些结构体的布局，其中就包括 struct module。因此，开启 KDB 后重新编译内核，struct module 的布局已经变了。而我的驱动模块是在未开启 KDB 的内核下编译的，其内部的 __this_module 副本仍是旧布局。替换新内核后，驱动模块没有重新编译，导致内核按新布局去读旧模块的结构体，最终崩溃。

如果编译 .ko 时使用的内核配置与当前运行内核不一致，struct module 的字段偏移量和总大小就会不同。此时内核按错误的偏移去读 name、size 等字段，就会读到错位的数据。

vermagic 只校验内核版本、SMP、Preempt 等少数宏观选项，无法覆盖所有影响结构体布局的配置。

然后重新编译一次 SDK （驱动也会一并编译）并且烧录进入板卡进行验证猜想。

4.验证#

重新编译之后烧录板卡，启动之后没有出现问题了，确认就是上述的问题导致的。

5.感想#

前后花费了一个小时来解决，主要是中间编译过程耗时间，没有一下次看出问题，而且也忘记了还有自动加载驱动这茬事情了，还是经验太少了。不过呢经过这次自己的调试经验又丰富了一些。
